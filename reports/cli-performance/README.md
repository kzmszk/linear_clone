# FUCHIKOMA-25のCLI性能比較

最終版 `7a84756` は、62操作を行う本番batchの中央値を **24.35秒から9.87秒**へ短縮しました。中央値の比は **2.47倍**です。目標の3倍には届いていません。単発コマンドの3倍改善も達成していません。

## 最終版の結果

| 本番での操作                           | 変更前の中央値 | 変更後の中央値 | 中央値の比 |
| -------------------------------------- | -------------- | -------------- | ---------- |
| 62操作の連続実行                       | 24.349秒       | 9.868秒        | 2.47倍     |
| `get-workspace-slug`                   | 217.7 ms       | 206.9 ms       | 1.05倍     |
| `project-filtered-list-workspace-slug` | 265.2 ms       | 250.4 ms       | 1.06倍     |
| `get-workspace-id`                     | 215.7 ms       | 166.1 ms       | 1.30倍     |
| `project-filtered-list-workspace-id`   | 264.7 ms       | 208.7 ms       | 1.27倍     |

連続実行は5試行ずつ、単発読取は20試行ずつです。変更前後を交互に実行しました。62操作は2 project作成、20 issue作成、10 issueを作業中へ変更、10 issue移動、20 issue完了です。変更前は62回のプロセス起動、変更後は1回のbatch起動です。batchでもコマンド同士は逐次実行します。

batchでは起動・HTTP接続を再利用し、最初にworkspaceのslugを一度だけUUIDへ解決します。この効果を単発コマンドの改善率とは扱いません。teamキー、project名、issue識別子、state UUIDを両版で使用しました。書込みfixtureは前後別のworkspaceに置き、各試行で同じ件数を増やしました。認可と競合検出は有効です。

計測区間はCLIのプロセス起動から終了までです。連続操作では逐次実行の制御時間も含め、fixture準備と保存結果の検証は含めません。各試行後にAPIを読み、20件のタイトル、移動先、完了状態、version 3を照合しました。元のproject Bは空です。

本番batchのp95は変更前25.083秒、変更後10.495秒でした。5試行ではp95は観測最大値であり、尾部レイテンシの安定した推定値ではありません。表の倍率は前後それぞれの中央値の比です。初期JSONの `medianSpeedup` もこの定義で、ペアごとの倍率の中央値ではありません。

## 調査で採用した変更

| 変更                        | 判断と根拠                                                                      |
| --------------------------- | ------------------------------------------------------------------------------- |
| workspace UUIDの直接使用    | ID確認のための一覧取得を省く。本番単発読取のUUID指定で1.27〜1.30倍              |
| metadataを1コマンド内で共有 | team・projectなど複数の名前解決を1回の読取にまとめる。次のコマンドでは取り直す  |
| 依存ライブラリのbundle      | 初期の起動のみの探索計測で約66.2msから52.3ms。minifyとcompile cacheは追加しない |
| foreground batch            | 常駐処理を作らず起動と接続を再利用。失敗時に停止し、成功済みの操作は保持        |
| 更新前の読取を並行          | issueと参照情報を並行取得し、両方の成功後に版番号付きで更新                     |
| state UUIDの直接使用        | Workerの所属検証を利用して不要な参照取得を省く。単独のレイテンシ改善は未確定    |

独自HTTP transportは探索的な読取で約21msの差でしたが、HTTP処理を二重に保守する変更は採用しませんでした。永続キャッシュ、常駐デーモン、Worker APIの追加は行っていません。

## 途中の結果と採用上の制限

- batch追加直後は23.856秒から10.077秒、2.37倍でした。
- 更新前の並行読取を加えた版は24.143秒から8.745秒、2.76倍でした。
- state UUIDの直接使用を加えた最終版は24.349秒から9.868秒、2.47倍でした。
- 並行読取版と最終版を同じ時間帯に直接2ペア比較すると10.410秒から10.226秒でした。探索計測であり、state UUIDの独立した改善効果とは断定しません。異なる時間帯の2.76倍と2.47倍の差を、この変更の退行と断定することもできません。

最もよかった途中の値を最終版の成果として採用しません。3倍達成には、最終比較の旧版中央値を基準に9.868秒を8.116秒以下へ短縮する必要があります。今後は残るHTTP・Worker書込み応答の待ち時間を分解して調査する必要があります。検証を省略したり、キャッシュを長寿命化したりして目標に合わせてはいません。

レビューでは、初期の共有fixtureによるデータ量・versionの差を修正しました。その修正前の測定を最終比較から除外しています。最終版に変更を加えた後、再計測しないまま過去の結果を転用してはいません。
