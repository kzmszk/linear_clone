# 完了条件と検証方法

実装と検証を進めている。実行済みの結果は [development-status.md](development-status.md) に記録し、以下のチェックリスト自体は動作保証とは扱わない。
ユーザーが求めるWeb・CLI・移行・同時処理・性能・読みやすさを、それぞれ別の合格条件にする。

現在のテスト対象・未検証範囲・性能変更前後の実行手順は [test-coverage.md](test-coverage.md) を参照してください。

## 必須の利用シナリオ

| 番号 | 実際に操作する入口                                   | 合格条件                                                                  |
| ---- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| E1   | Webで作成→編集→一覧→詳細→削除→復元                   | CLIで同じ値が読める。reload後も保存されている                             |
| E2   | ビルド済みCLIで同じ操作                              | 別のブラウザーセッションに反映される。JSONと終了コードが正しい            |
| E3   | workspace/team/project/member管理                    | 作成・変更・所属解除がWebとCLIで一致。projectの複数team所属も保てる       |
| E4   | 権限の異なる2人、2workspace、private team            | 他workspaceのID・ファイル・コメント・イベント・receiptを取得できない      |
| E5   | メンバー除外・token期限切れ・再接続                  | 接続が閉じ、cacheが消え、HTTP再読込も拒否される                           |
| E6   | 日本語本文・表・チェックリスト・コード・リンク・画像 | 編集、保存、再読込、CLI取得で内容を保つ                                   |
| E7   | 自分と別セッションが同じチケットを編集               | 確定値か明示競合が返り、入力したdraftが黙って消えない                     |
| E8   | 一覧のfilter・sort・cursor・戻る                     | 重複や欠落がなく、戻ると位置とfilterを保つ                                |
| E9   | API応答切断、reload、socket切断、runtime再起動       | 同じoperationIdの再試行で重複せず、再取得で保存済み変更と削除を確認できる |
| E10  | backupを空のインストールへrestore                    | 件数・本文hash・参照・ファイルが一致する                                  |
| E11  | 初回bootstrap、再送、再起動、別本人の同時要求        | 指定本人だけが初期管理者になり、workspaceが重複せず初期化が閉じる         |
| E12  | 招待受諾と再送、未招待本人、新workspace作成          | 検証済み本人への所属だけが作られ、作成権限と最後の管理者を守る            |
| E13  | project・member・comment等の同じversionを並行更新    | 片方が成功し片方が競合、同じ操作の再送は重複効果を持たない                |

Playwrightは実際のブラウザーから、CLIテストは実行ファイルをsubprocessとして起動する。
対象は本物のWorker runtimeとSQLite/R2 binding。
ローカルのprovider代替は本人確認の入口だけに限定し、認可・データ処理は本番と同じ経路を通す。
本番向けbundleにテスト認証を含めない検査を行う。
デプロイ先では本物のAccess認証、期限切れ・署名不正・audience不正の拒否を別途確認する。

テストは公開APIや画面の結果へliteralな期待値を置く。
DB関数をモックして呼び出し回数を見るテスト、実装の式をそのまま期待値にしたテストは作らない。
小さな単体テストを足す場合も、Markdown変換の欠落やcursorなど、実際の不具合を検出するものに限定する。

網羅するのは日常操作、起こりやすい通信失敗、保存済みデータや権限に影響する失敗、指定された同時処理である。
まれな障害の組み合わせを際限なく増やさず、データを壊さずエラーを返して手動再試行できればよいケースを認める。
reload後の未保存draft復元・自動再送、無停止のLinear移行は合格条件に含めない。
未保存のまま画面を離れる警告と、再読込後にサーバーの保存結果を確認する導線を検証する。

## 100件同時処理

同じテストをローカルとCloudflareの隔離した検証用インストールで実行する。
localhostでの結果をCloudflareの性能と呼ばない。

1. 同じteamに100件を一斉送信する。送信時刻の最大差を記録し、100ms以内を目標とする。
2. 各createのoperationIdを再送する。作成件数は100件のままで、receiptの識別子が一致する。
3. 返された各versionに対して100件の更新を一斉送信する。
4. 100件すべてのタイトル・本文・status・versionをGETとCLIで照合する。
5. runtimeを再起動し、同じoperationIdを再送して保存結果が変わらないことを確かめる。
6. 別試験で1件の同じversionへ100更新を送る。1成功・99競合、確定履歴は1更新になる。
7. 応答だけを遮断してcommit後に再送するケースも確認する。

重複ID、採番衝突、黙った上書き、成功応答後の消失を0件にする。
create burstとupdate burstを各3回行う。
各リクエストのp50/p95/max、初回失敗、再試行、409、5xx、全件確定までの時間を残す。
3〜5人の想定リージョンから、100件burstを再試行込み15秒以内、各要求のp95を5秒以内とする暫定目標を置く。
この数値は設計目標であり、ユーザーが指定した既存のSLAではない。

DBの件数を直接見るだけで合格にしない。
API一覧とCLI、Webの表示でも最終状態を確認する。
CPU時間、SQL rowsRead/rowsWritten、Object容量、ファイル容量を同時記録し、無料枠の残量と比較する。

## Linearとの速度比較

「きびきび動く」を次の観測値に分ける。

| 観測値                   | 始点と終点                                 | 暫定目標               |
| ------------------------ | ------------------------------------------ | ---------------------- |
| 操作の表示反映           | pointer/keyboard入力→内容が表示されたframe | warm操作のp95 ≤100ms   |
| 編集可能になるまで       | 詳細・作成画面を開く操作→入力可能なeditor  | warm操作のp95 ≤100ms   |
| 保存確定                 | 保存送信→永続化成功の応答                  | 通常単発操作p95 ≤500ms |
| 他セッションで見えるまで | 保存送信→2人目が確定versionを表示          | p95 ≤1,000ms           |
| cold起動                 | navigation開始→最初の一覧が操作可能        | p95 ≤2,000ms           |

上記だけでは「Linearとほぼ同等」の証明にならない。
同じマシン・ブラウザー版・viewport・倍率・回線・近い件数と本文サイズで、Linearとcloneを交互に測る。
一覧→詳細、作成ダイアログ、プロパティ編集、削除後の一覧を各30回以上測る。
coldとwarmを別にし、失敗trialを黙って除外しない。
比較条件として `clone p95 <= max(Linear p95 * 1.2, Linear p95 + 20ms)` を暫定採用する。
保存確定の差は表示の差と別列にする。

ブラウザー内の入力時刻・DOM表示条件・animation frameとChromium traceを使う。
DOMが変わっただけで画面に描画されたとは断定せず、代表trialのfilmstripを照合する。
自動操作ツールの往復時間をアプリのレイテンシとして測らない。
cloneだけ計測に都合のよいDOMマーカーを使い、Linearでは通信完了を待つような非対称の比較を避ける。

現在のLinear調査は読み取りに限る。
作成・保存・削除の比較は、許可された使い捨てチケットを使う検証環境で行う。
その計測環境を用意できない場合、該当項目は未検証とし、画面遷移だけで全操作の同等性を宣言しない。

## UIの近似と操作性

実画面を基準に、左ナビ・上部breadcrumb・密な一覧・右プロパティ・作成dialogを比較する。
ライトテーマを初期基準にし、ダークテーマも同じ配置で用意する。
一覧と詳細を1440×900と狭いviewportで比較し、スクリーンショット差分をレビューする。
フォントの描画差や動的データはmaskし、全面一致率だけで見た目の合格を判断しない。

| 画面群             | 見た目と操作の確認対象                                  |
| ------------------ | ------------------------------------------------------- |
| workspace/team管理 | 設定ナビ、一覧とフォーム、切替、保存状態、権限不足      |
| project管理        | 一覧・詳細・編集、status、複数team所属、archive         |
| member管理         | メンバー一覧、招待、ロール変更、除外、最後のownerの保護 |
| 削除・復元         | 確認dialog、一覧からの反映、復元導線、戻る時の選択位置  |
| 失敗・競合         | 保存中表示、draft保持、再送・破棄・比較、focusの位置    |

対応するLinear画面を参照できるものは並べて比較する。
clone固有の復元・競合状態は同じ色・余白・文字・dialog規則を使い、主要CRUDと同じキーボード検査を行う。

最低限のキーボード操作は、作成、検索、行移動、開く、閉じる、戻る、保存。
Tab順、dialogのfocus trap、Escape、IME変換中のショートカット誤発火、スクリーンリーダー用labelもE2Eに含める。
仮想一覧の画面外要素を操作しようとするテストは、表示までscrollしてから操作する。

## 移行の合格条件

実データは公開fixtureへコピーしない。
同じ構造の合成fixtureを使った再現試験と、実exportとのprivateな照合を分ける。
sourceの全connectionが完了したmanifestから期待件数を作る。
現時点の289件は調査時点の数字であり、今後の全テストに固定してsource変更を異常扱いしない。

- archiveを含むチケット件数が一致する。
- title、description、status、priority、日時、source IDが一致する。
- parent、relations、labels、project-team、author、comment threadの対応が一致する。
- 原本JSONとrich-text表現のhashが一致し、取得フィールド・schema版を追跡できる。
- historyの件数、actor、日時、変更対象が一致し、activityに重複なく表示される。
- コピーしたLinearホストの全ファイルのchecksumが一致する。
- importを同じrunと別runで再実行しても重複しない。
- entity、relation、fileの途中で中断して再開できる。
- 移行先で編集・削除したレコードを再importが黙って上書き・復活させない。
- 取得不可の情報は項目名と理由を報告し、欠損が残る限り完全互換とは表示しない。
- Linearへのアクセスを使わず、cloneだけでコピー済み画像が表示できる。

## 開発チェックと証拠

### ソースコードの品質

機能が動いていても、責務の混在・過度な複雑さ・業務ルールの重複・実際の処理と異なる命名が残る変更は完了扱いにしない。
実装者は各commit前に差分を読み、[AGENTS.md](../AGENTS.md) の基準で確認する。
HTTP routeやTrackerへ個々の業務処理が集まり始めたら、[モジュールの責任](modules.md) に戻して分離する。

[oxlint設定](../.oxlintrc.json) にファイル行数、関数行数、循環的複雑度、ネスト深度の制限を置く。
数値以内でも読みにくいコードは修正する。行数を減らすだけのhelper分割や、早すぎる共通化は合格にしない。
lintで機械的に判断できない命名・責務・重複は、コードレビューで確認する。
開発基盤の構築時には、この設定を `pnpm check` とpre-commitから実行し、違反するコードが拒否されることも確認する。

### 実行と記録

実装後の共通入口を `pnpm check` とし、format:check、lint、typecheck、build、必要な実動作テストをまとめる。
Web E2Eは `pnpm test:e2e`、負荷試験は `pnpm test:load` として単独でも再実行可能にする。
pre-commitは変更ファイルと型検査。E2Eを全コミットのhookへ押し込まない。
hookが正常なcommitを通し、型エラーを拒否することは使い捨てrepoで確認する。

結果にはcommit SHA、実行コマンド、runtime版、対象URL、DB初期化方法、実行時刻を付ける。
trace、スクリーンショット、JSON比較、負荷測定の生データは成果物として保存する。
privateな内容を含むartifactはgitの外へ置き、公開可能な集計だけをcommitする。
各条件の結果は VERIFIED / NOT VERIFIED / INCONCLUSIVE で表す。
